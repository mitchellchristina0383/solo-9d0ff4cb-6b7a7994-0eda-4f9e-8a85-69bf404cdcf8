# VPN 换线 · MTU 黑洞演练台 ＋ 夜间备份双路排班（Flask + Docker Compose）

一个单页交互式工具，包含两块相互联动的功能：

1. **MTU 黑洞 / 换线演练**，复现典型故障：

> VPN 换线后小包能通、大报表卡住。报文置 DF 禁止分片，一旦
> `载荷 + 封装开销 > 线路 MTU` 就在线路侧被丢弃；超长通知（ICMP too-big）
> 可能被过滤形成静默黑洞，只能等超时缩包。换线后载荷重新从起始值试发，
> 旧线在途报文的回执仍会到达，与新线回执乱序交错、区间重叠。

2. **夜间备份排班（A/B 双线路整班排线）**：网管改线路参数时，必须保住
   各分支已约定的时段与速率。按分支录入备份的起止分钟、固定报文载荷、
   保底速率，排布器枚举全部 `2^12` 种 A/B 分配（单班最多 12 单），满足：
   - 每单全程只走一条线；
   - `固定载荷 + 该线封装开销 ≤ 该线 MTU`；
   - 同一条线在任意时刻，重叠预约的保底速率之和 `≤ 该线可用带宽`。

   **加单或应用新线路参数都会整班重排**；可以先调 `/api/schedule/plan`
   试排（不落库，当前安排照常可查）。提交在一把锁内“先排后交”：加单按
   届时有效的线路参数与已有预约排，改参也必须安置届时已接的单。排得下，
   新单/新参数与新走线一并生效，且**成功应用参数会照常重置发包演练**；
   排不下，返回中文原因（指出单号、时段、哪条线、超多少），**原演练、
   原预约与原走线全部保留**。

## 启动

### Docker Compose（推荐）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

镜像用 `python:3.12-slim`，入口为 `gunicorn -w 1 --threads 8`
（内存态演练，必须单 worker；多线程足够单人/小班使用）。
`compose.yaml` 带 `/healthz` 健康检查。

### 本地直接运行

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
python app.py            # http://127.0.0.1:8000
```

跑测试：

```bash
pip install -r requirements.txt pytest   # pytest 不在运行依赖里
pytest                   # 34 个 API/引擎/并发用例
```

## 页面能做什么

1. 填写 **报表字节数**、**起始载荷**、**超时缩包步长**；
2. 分别设置 **线路 A / B 的 MTU、封装开销、超长通知开关**，
   参数卡实时显示 `MTU - 封装开销` 的最大载荷以及起始包是否必超；
3. **发下一包** / 填数量 **连续发包** / **连续发完剩余新包**；
4. 每个在途包可单独点 **回执 ACK** 或 **触发超时**；
   也可选择正序 / 逆序 / 随机乱序，**依次批量回执**，或只随机回一个；
5. 超长通知打开时，超大包被丢弃并产生“待投递通知”，由你手动点
   **投递超长通知**（可以先换线再投递，观察“过期轮次通知不缩包”）；
6. **换到线路 A/B 并立即重发**：载荷重置为起始载荷、轮次 +1，
   并按新载荷把所有未确认字节重新打包立即发出；
7. 表格显示每包的 **线路、轮次、类型、载荷长度、封装后长度、
   字节区间 `[起,止)`、协议状态与上帝视角的物理结果、操作按钮**；
8. 顶部实时显示 **累计确认字节数 / 总字节数 / 百分比**、合并后的确认区间、
   区间 chip 和覆盖图（绿色为确认区间，彩色描边为各包范围）；
9. `累计确认 == 报表字节数` 时显示“全部传完”横幅，并发新包/换线会被拒绝，
   重复/重叠回执保持幂等。

**夜间备份排班（页面顶部独立卡片）：**

10. 在线路 A / B 参数卡设置 **MTU、封装开销、可用带宽（Mbps）、通知开关**；
11. 按分支录入 **起始分钟、结束分钟、固定报文载荷、保底速率**，
    点 **加单并整班重排（提交生效）**；也可 **只试排这单（不提交）**
    先看候选走线与原因，下方当前安排不变；
12. 预约表列出每单的 **线路 A/B**、分钟区间与 `HH:MM` 时刻；容量区显示
    两线 **峰值速率 / 可用带宽** 占用条和各原子时段的速率 chip；
13. 支持 **立即整班重排**（不保留稳定偏好、选最均衡方案）、
    **删除并重排**、两击确认的 **清空班次**、**灌入演示班次**；
14. 改完线路参数点 **应用参数并重置演练**：先过排班闸门，排得下才让
    新参数 + 新走线生效并重置演练；排不下弹红色原因面板，参数不生效，
    原演练（报文/轮次）与原预约/走线都保留。

## 核心规则与实现对应

代码分三层：

- `drill_engine.py`：MTU 演练纯逻辑。`Drill`（演练状态）、`Packet`、
  `DrillConfig/LineConfig`（线路参数含 `bandwidth` 可用带宽）、
  `AckedRanges`（合并区间并集与未确认打包）。
- `schedule_engine.py`：夜间备份排班纯逻辑。`BackupOrder`、`Plan`、
  `ShiftBoard`（已提交班次）、`plan_shift()`（≤12 单全枚举排布 +
  中文诊断），以及输入解析/时段负载分析。
- `app.py`：Flask 路由 + 全局 `Drill` / `ShiftBoard` 单例 + 一把 `RLock`，
  所有响应回传完整 state（含 `schedule`）。
- `templates/index.html`、`static/app.js`、`static/style.css`：原生 JS 单页，
  无外部 CDN/依赖，每 2.5s 轮询一次，所有写操作后立即用响应 state 重渲染。

### 排班与并发语义

- **排布是精确的全枚举，不是启发式**：n≤12 → 至多 4096 个掩码。
  `bit i = 1` 表示第 i 单走 B。先用 MTU 禁位掩码过滤，再用全局事件增量
  （开始 `+rate`、结束 `-rate`，同一时刻的增减合并）一次扫描得到该分配下
  A/B 两线峰值；`peak ≤ bandwidth` 才可行。端点相接 `[0,60)`/`[60,120)`
  合并在同一事件点处理，不会误判重叠。
- **确定性选优**：在可行方案中依次最小化 `(相对当前走线的改动数,
  两线峰值利用率最大值, 利用率平方和, 掩码)`，因此默认尽量不动既有走线、
  再做负载均衡，小号单在平局时优先 A。
- **失败原因**：区分“两条线 MTU 都放不下”“MTU 强制单线的单在该线挤爆”
  “全班总速率超过 A+B 带宽和（怎么分都不行）”以及“枚举全部方案后最接近
  的瓶颈时段”，每条都带单号/分支/分钟时段/速率数值。
- **交错提交**：Flask 用单进程单 worker + 多线程，全局 `RLock` 把
  “校验 → 排布 → 提交”串行化。每个加单/改参请求都在拿到锁后读取届时
  最新的 `LineConfig` 与 `ShiftBoard`，因此交错请求等价于某个串行顺序；
  排不下时在改任何状态之前抛 `ScheduleError(409)`，错误响应还回传当前
  未改动的完整 state。试排 `/api/schedule/plan` 是纯函数计算，绝不提交。

关键语义：

- **字节编号**：从 0 开始，区间左闭右开，`[0,1400)` 即前 1400 字节。
- **DF 判定**：发包时计算 `wire = size + overhead`，`wire > mtu` 即物理丢弃：
  - 通知关 → `silent_drop`：发送端仍显示“在途”，且不允许 ACK（上帝视角标明
    实际已静默丢弃），只能由演练者点“触发超时”；
  - 通知开 → `notify_drop`：生成 pending 的超长通知，可手动投递。
- **轮次（round）**：每包盖当前轮次号。一次有效的通知缩包或超时缩包会让
  轮次 +1。旧轮次包的通知/超时只记录事件、**不再缩包**。超时若来自当前轮，
  载荷减一个步长（下限 1），并立即用新载荷重发最早的未确认连续段；
  超长通知则把载荷降到 `MTU - overhead`。
- **换线**：`active_line` 切换、`cur_payload = start_payload`、轮次 +1，
  然后调用 `resend_missing(kind="switch")` 立即重发全部未确认字节。
- **回执与去重**：ACK 把包区间加入 `AckedRanges` 的合并区间并集，
  返回本次“新增字节数”；重叠/重复区间新增 0，累计确认只按并集长度计算一次。
  超时后的在途包仍可“补到迟到回执”，并打 `late_ack` 标记。
- **重发只取未确认字节**：`AckedRanges.packetize_unacked(max_len)`
  跳过所有已确认区间，把未确认字节按当前载荷切成连续段；遇到已确认区间
  立即断段，所以重发包可能短于设定载荷。
- **规模保护**：报表 ≤ 1,000,000 字节，最多 5,000 个包；“连发全部”前先估算包数，
  超限直接 400 且不改状态。

## API 一览

| 方法/路径 | 作用 |
| --- | --- |
| `GET /api/state` | 完整演练状态 + `schedule` 排班状态 |
| `GET /api/schedule` | 仅排班板（预约、走线、两线时段负载） |
| `GET /api/orders` | 预约单列表（附 `schedule`） |
| `POST /api/orders` | 加单并整班重排、原子提交（别名 `/api/backups`、`/api/schedule/orders`、`/api/schedule`） |
| `POST /api/schedule/plan` | **试排不落库**：可带 `{"order":{...}}` / `{"orders":[...]}` / `{"lines":{...}}` |
| `DELETE /api/orders/<id>` | 删除并整班重排（另有 `POST .../delete` 别名） |
| `POST /api/schedule/replan` | 不受当前走线偏好约束，全局重选最均衡方案 |
| `POST /api/schedule/clear` | 清空班次 |
| `POST /api/schedule/demo` | 灌入 4 单演示班次（覆盖当前班） |
| `POST /api/line-params` | 应用 A/B 参数并重置演练（可只发 `{"A":{...},"B":{...}}`）；排不下返回 409 且状态不变 |
| `POST /api/reset` | 用完整 JSON 参数重置（空体=默认参数）；同样先过排班闸门 |
| `POST /api/send-next` | 发下一包（优先推进新字节，否则补最早缺口） |
| `POST /api/send-burst` | `{"count": 8}` 连发；`{"count":"all"}` 发完剩余新字节 |
| `POST /api/resend-missing` | 按当前载荷重发全部未确认字节 |
| `POST /api/switch` | `{"line":"B"}` 换线、重置载荷并立即重发 |
| `POST /api/packets/<id>/ack` | 回执（支持超时后的迟到回执，重叠自动去重） |
| `POST /api/packets/<id>/timeout` | 触发超时（仅当前轮缩包并重发） |
| `POST /api/packets/<id>/deliver-notice` | 投递超长通知（旧轮通知被忽略） |
| `GET /healthz` | 健康检查 |

预约单 JSON 字段（同时接受常见别名）：`branch`、`start_minute`
（别名 `start`）、`end_minute`（`end`）、`payload`（`fixed_payload`）、
`rate`（`guaranteed_rate`/`min_rate`）。线路对象在原 `mtu`/`overhead`/
`notify` 之外新增 `bandwidth`（可用带宽，Mbps，默认 100）。

错误统一为 `{"ok": false, "error": "..."}`，排班错误另带
`"reasons": [...]`、`"plan": {...}` 与未改动的 `"state"`：400 参数问题、
404 找不到包/单、409 当前状态冲突（排不下、超 12 单、ACK 已丢弃包等）。

## 推荐手动演练脚本

**A. 静默丢包（默认参数即是此场景）**

1. 默认 `报表 10000 / 起始载荷 1400`，A 线 `1500 / 120 / 通知关`
   （最大载荷 1380），B 线 `1500 / 60 / 通知开`（最大载荷 1440）；
2. 连发包数填 8，点“连续发包”：前面的满包显示红色“静默丢弃”，
   最后一个短包可能实际在途——这就是“小包能通、大包卡住”；
3. 尝试给红色静默丢包点 ACK 会被拒绝；对它点“触发超时”：
   载荷 `1400 → 1200`、轮次 +1，并自动重发 `[0,1200)`；
4. 对在途包任意顺序 ACK，再点“重发全部未确认”，直到绿色“全部传完”。

**B. 换线后的回包交错与重叠去重**

1. 可用测试里的参数：报表 `4200`，A 线开销 `200`（最大载荷 1300，通知关）；
2. 连发 3 包 → 对 `#1` 超时缩到 1200 → ACK 重发包 `#4` → “重发全部未确认”；
3. 在任何回执前点“换到线路 B 并立即重发”：载荷回到 1400，
   新包区间从尚未确认的 1200 开始，与 A 线在途包大面积重叠；
4. 用每包按钮按 `B#9 → 旧A#5 → B#8 → 旧A#6 → B#10` 的顺序回执，
   可看到累计确认 `2600 → 3800 → 4000（重叠只 +200）→ 4000（完全覆盖 +0）
   → 4200 传完`；给旧 A 线包补超时会提示“旧轮次不缩包”，但之后仍可迟到 ACK。

**C. 超长通知轮次**：点“预设：A 有超长通知”，连发 3 个满包后，
先投递任意一个通知：载荷一次性降到 1380；再投递同批其它通知，
会显示“过期轮次通知·已忽略”，不会重复缩包。

**D. 夜间备份整班排线 / 改参保约**

1. 点 **灌入演示班次**：甲单载荷 1400 被 A 线 MTU（上限 1380）逼到 B，
   其余单按带宽均衡分到 A/B，容量条显示峰值；
2. 把某单速率改大后点 **只试排这单（不提交）**：红色面板给出冲突时段与
   原因，但表格/角标不变；再点 **加单并整班重排**，失败时 toast + 红面板，
   原单一条不少；
3. 先在演练台发一个包留下标记，再把 A/B **可用带宽都改成 1**，点
   **应用参数并重置演练**：返回 409 与原因，排班和线路带宽不变，
   演练台那个包/轮次也还在；改成大带宽后再应用：成功，演练回到第 1 轮、
   报文清空，所有预约按新参数重新走线；
4. 连续加到第 13 单会被拒绝并提示“单班最多 12 单”。

## 实测结果（交付前）

沙箱内没有 Docker 守护进程/CLI，因此镜像构建与 Compose 起容器未能在此执行；
已用同一解释器虚拟环境与 Dockerfile 同款 gunicorn 命令完成以下验证：

- `pytest`：**34 passed**（原 10 个 MTU 演练用例全部保持通过 +
  新增 24 个排班用例）。排班部分覆盖：MTU 强制选线、带宽边界相等可行、
  相邻时段不重叠、三单 60/两线 100 不可行、超 A+B 总带宽诊断、双线 MTU
  都放不下诊断、12 单上限、失败不消耗单号/不改 assignment、试排不落库、
  不可行加单保留预约、可行改参整班改线并重置演练、不可行改参同时保留
  **演练报文/轮次**与预约/走线/旧带宽、删除/重排/演示、
  **8 线程并发加单恰好 12 成 4 拒**、**4 加单线程 + 2 改参线程 + 2 读线程
  交错 1 秒无 5xx 且最终状态逐分钟带宽/MTU 不变量成立**、脚本化两种提交
  顺序验证“按届时参数排布”；
- **真机 HTTP 走查**（gunicorn `-w 1 --threads 8 -k gthread
  -b 127.0.0.1:8011 app:app`，脚本 `/tmp/livecheck/run_check.py`）：
  4 单演示分配 `甲→B / 乙→A / 丙→A / 丁→B`；试排 9999Mbps 候选返回原因且
  `GET /api/schedule` 前后完全一致；不可行加单 409 后仍是 4 单、演练标记
  保留；带宽改 1/1 的 `/api/reset` 409 后旧带宽 100 与演练包都在；
  A 开销改 1499 + B 带宽 200 后 4 单全部改走 B 且演练重置（packets=0,
  round=1）；最后对真实 gunicorn 跑 3 秒多线程交错，**209 个请求
  （126×200 / 83×409）、0 个 5xx、读请求全 200**，最终 12 单且不变量通过；
- **jsdom 真实页面冒烟**（加载 Flask 渲染的 HTML + 真实 `static/app.js`，
  Node 22 + jsdom）：**21 项断言全过、无 JS 错误**，包括录单后表格出现
  “线路 B/A”、角标 1/12→2/12、试排红面板说明带宽且不落库、不可行改参
  显示“未生效”且服务端带宽仍为 100、可行改参落为 1000、删除、跨过
  2.5s 轮询重渲染无异常、演示班渲染；`node --check static/app.js` 通过；
- 排布器性能：初版每个候选都重建分段/格式化字符串，12 单最坏约 **580ms**；
  改为 MTU 禁位掩码 + 全局事件增量扫描后，同机最坏约 **40–60ms**
  （共享宿主 CPU 有争抢），典型共享窗口班次更低；锁内只做内存计算，
  读接口最多等待这几十毫秒；
- `compose.yaml` 通过 PyYAML 解析，端口 `8000:8000` 与 `/healthz`
  healthcheck 命令形状正确；用 Dockerfile 同款 gunicorn 命令实际启动并
  验证 `/healthz`、`/api/state`（含 `schedule`）正常；
  `requirements.txt` 的版本区间对应实测可用的 Flask 3.1.3 / gunicorn 27.0.1。

## 限制与余项

- **单班次、单实例、内存态**：全局一把锁，刷新页面状态还在（同一服务进程），
  但重启即丢；“单班 12 单”是全局唯一班次，不支持多班组/多房间隔离，
  如需多人同时使用要加 session/房间维度与持久化。
- 时间用 **0–1440 当天分钟**、区间左闭右开；跨午夜备份需把夜班起点记为 0
  换算成连续分钟（校验会拒绝 `start>=end` 并提示），尚未做自动跨天拆分。
- 速率/带宽按 **Mbps** 同单位数值处理（支持小数，比较带 `1e-9` 容差），
  没有做 kbps/Gbps 单位换算；排布目标只保证可行 + 稳定/均衡，不优化
  费用、时延或主备亲和等其它策略。
- 这是**协议行为与排班约束仿真**：不发真实 ICMP、不操作真实网卡/路由、
  不下发真实 VPN 配置；“上帝视角”的物理丢弃标记是教学设计。
- 超时由演练者手动触发（不做真实倒计时）；页面有 2.5s 轮询但没有自动发包。
- 本沙箱无 Docker，**`docker compose up --build` 未在本机实跑**；
  已用同款 gunicorn 启动验证，首次在有 Docker 的机器构建时需确认网络可拉取
  `python:3.12-slim` 与 pip 依赖。新模块 `schedule_engine.py` 在构建上下文内
  （`.dockerignore` 未排除它）。
- 未做鉴权与审计，仅限本地/可信教学网络；不要直接暴露到公网。
